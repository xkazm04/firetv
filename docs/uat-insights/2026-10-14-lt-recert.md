## 3. Methodology lessons

- **A recertify on a changed instrument cannot certify.** `recertify.md` did the right thing: it named the confound and listed the verdict drops. But 25 "fixed" and 10 "drops" now rest on the same unproven ground. **Proposal:** the ledger refuses `fixed` (it writes `not-seen`) when the driver hash differs, and the next run pins the driver at 05229633e55bf1b7 / 05535a9f66962fd0 so the following recertify is like for like.
- **A new finding can be a regression with no prior row.** Tomas was placed exact (A1) in `lt` and B1 here. No `lt` row existed to recur, so `recertify.md` shows `Regressed: none` while the placement got worse. **Proposal:** recertify diffs `facts.placement.band` per Character as well as finding rows.
- **The stored placement facts replay exactly.** All ten `recert-1` J1 placements give the stored band and confidence back through `staircase()` at 7e6b6897 (`tools/linga-rules-test.cjs`, LG-48). A placement rule change can therefore be gated on stored marks with no model call. The facts keep no `skipped` flag, so the replay reads a task with no response and a "Skipped" note as a skip.
- **Duplicate re-raises again.** The placement is re-raised in every journey (23 rows for one defect per Character), and the TV/phone label in four. The counts above are per row, as `recertify.md` gives them, so they overstate distinct defects.
